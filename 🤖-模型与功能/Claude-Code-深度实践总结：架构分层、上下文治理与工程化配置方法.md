## 摘要

Tw93 这篇长文围绕一个核心判断展开：**Claude Code 的问题，很多时候并不是 Prompt 不够强，而是整套系统的上下文、工具、技能、子代理、Hook 与验证机制没有被工程化治理**。

作者结合近半年深度使用经验，提出应当把 Claude Code 理解为一个由多层系统组成的代理框架，而不是简单的聊天机器人。文章重点讨论了以下几个方面：

* Claude Code 的底层运行机制
* 为什么上下文会逐渐失控，以及如何治理
* MCP / Plugin / Tools / Skills / Hooks / Subagents 的概念边界
* Skills 应如何设计成按需加载的工作流
* 为什么 Prompt Caching 是 Claude Code 架构中的关键
* 怎么写一个真正长期有效的 `CLAUDE.md`

## 一、Claude Code 不是聊天工具，而是一个代理循环系统

文章首先指出，Claude Code 的核心不是"回答问题"，而是一个不断循环的代理执行过程。

作者认为，实际使用中大多数卡点并不是模型智力不足，而是以下问题造成的：

* 上下文提供错了；
* 中间产物污染了上下文；
* 工具太多导致选择混乱；
* 规则写太长反而自我污染；
* 验证闭环缺失，导致结果无法判断对错。

因此，理解 Claude Code，不能只从 Prompt 入手，而需要从系统层面拆解和约束。

## 二、用"六层系统"理解 Claude Code

作者提出，应把 Claude Code 拆成多个层级来看。虽然原帖中图示没有直接展开在文本里，但文章整体所强调的治理对象主要包括：

* Prompt / 指令层
* 上下文层
* 工具层
* Skill 工作流层
* Hook 控制层
* Subagent 隔离执行层
* 验证与回收层

作者的观点是：**如果只强化其中一层，而忽视其他层，系统就会失衡。**

例如：

* `CLAUDE.md` 写得过长，会先污染上下文；
* 工具数量过多，会导致模型选错工具；
* Subagent 滥用，会带来状态漂移；
* 缺乏验证，则根本无法判断产出是否正确。

## 三、概念边界：MCP / Plugin / Tools / Skills / Hooks / Subagents

文章给出了一个很实用的边界划分：

* **Tool / MCP**：给 Claude 增加新的动作能力
* **Skill**：给 Claude 增加一套工作方法或任务流程
* **Subagent**：在隔离环境中执行特定子任务
* **Hook**：在执行前后强制插入规则、审计或自动处理
* **Plugin**：用于跨项目分发能力

这部分的核心价值在于帮助团队明确：**到底是要扩能力，还是要控流程，还是要隔离执行。**

## 四、上下文工程：问题往往不是"不够长"，而是"太吵了"

这是整篇文章中最重要的一部分之一。

作者认为，大多数人错误地把上下文问题理解为"容量不够"，但真实情况更常见的是：

* 有价值信息被大量低价值内容淹没；
* 固定工具定义占用大量上下文空间；
* 长会话中的中间产物不断污染上下文；
* 自动压缩把关键决策理由也一起删掉了。

### 文中强调的几个实践建议

#### 1. 保持 `CLAUDE.md` 简短、硬、可执行

优先写：

* 命令
* 约束
* 模块边界
* 必须保留的信息

不要把大量参考资料直接塞进 `CLAUDE.md`。

#### 2. 大型文档拆给 Skills supporting files

文章建议，把重资料拆到 supporting files，而不是堆进 `SKILL.md` 正文。

#### 3. 路径/语言规则放进 `.claude/rules/`

不要让根级 `CLAUDE.md` 承担所有差异化规则。

#### 4. 主动管理上下文生命周期

作者建议：

* 长会话中用 `/context` 观察消耗；
* 任务切换优先 `/clear`；
* 同一任务进新阶段时考虑 `/compact`；
* 把压缩保留项写进 Compact Instructions。

#### 5. 使用 `HANDOFF.md` 替代依赖自动压缩摘要

作者提出一个非常实用的做法：在开启新会话前，先让 Claude 写一份 `HANDOFF.md`，记录：

* 当前进展
* 已尝试路径
* 哪些方法有效
* 哪些是死路
* 下一步建议

这样新的 Claude 实例只需读取这个文件，即可接续任务，而不必依赖压缩算法的摘要质量。

## 五、Plan Mode 的工程价值：先探索，再执行

作者对 Plan Mode 的评价很高，核心原因是它把"探索阶段"和"执行阶段"拆开了。

价值主要体现在：

* 探索阶段尽量只读，不改文件；
* Claude 可以先澄清边界和方案；
* 真正的执行成本在计划确认之后才发生；
* 对复杂迁移、跨模块改动、重构任务尤其有效。

作者还提到一个进阶玩法：

* 用一个 Claude 写计划；
* 再让另一个模型或代理以"高级工程师"角色审这个计划。

这是一种"AI 审 AI"的工程化协作方式。

## 六、Skills 设计：不是模板库，而是按需加载的工作流

文章特别强调，Skill 的价值不是"保存 Prompt"，而是把任务语义、执行骨架和 supporting files 组合成可按需加载的工作流。

### 一个好 Skill 应具备的特征

* 描述的是"什么时候该调用我"，而不是"我是什么"
* 有完整步骤、输入、输出和停止条件
* 正文只保留导航和核心约束
* 大资料放 supporting files
* 有副作用时要明确关闭模型自动调用

### 典型 Skill 类型

作者总结了三类常见 Skill：


1. **检查清单型**：用于发布前或交付前质量门禁
2. **工作流型**：用于高风险、标准化操作，如迁移与回滚
3. **领域专家型**：用于封装诊断路径和证据收集框架

### 文中提出的 Skill 反模式

* description 太模糊，例如"help with backend"
* `SKILL.md` 正文过长
* 一个 Skill 覆盖太多不同任务
* 有副作用的 Skill 还允许自动调用

## 七、工具设计：给 Agent 用的工具，不等于给人用的 API

作者认为，给 agent 设计工具时，目标不是"功能足够全"，而是"更不容易被用错"。

### 几个实用原则

* 工具命名按系统或资源分层，例如 `github_pr_*`、`jira_issue_*`
* 大响应支持 `concise / detailed`
* 错误响应要告诉模型如何修正
* 能封装高层任务时，不要暴露过多碎片工具

文中还举了一个很有代表性的例子：

为了让 Claude 在中途停下来问用户，团队尝试过：


1. 给已有工具增加 `question` 参数
2. 让模型按特定 markdown 输出提问
3. 做成独立的 `AskUserQuestion` 工具

最终第三种效果最好，因为它让"提问"这个动作变成了强制性的显式工具调用，减少了歧义和遗漏。

## 八、Hooks：把不能交给模型临场发挥的事，收回确定性流程

作者把 Hook 理解为：**把某些不能依赖 Claude 临场记忆和临时发挥的动作，重新纳入确定性工程流程。**

适合放进 Hook 的内容包括：

* 禁止修改受保护文件
* 编辑后自动格式化、lint、轻量校验
* SessionStart 时注入环境信息
* 任务完成后推送通知

不适合放 Hook 的内容包括：

* 需要大量上下文理解的复杂语义判断
* 长时间运行的业务流程
* 需要多步推理的决策

文章还强调，Hook 输出要尽量短，否则它自己也会变成新的上下文污染源。

## 九、Subagents：价值不只是并行，更是隔离

作者指出，Subagent 的真正价值不只是并行执行，而是**把会产生大量中间产物的任务隔离出去**。

适合交给 Subagent 的任务包括：

* 扫描代码库
* 跑测试
* 做审查
* 大量信息收集

主线程只拿摘要，而不接收全部中间输出，从而避免污染主上下文。

### 配置时应显式约束的内容

* `tools / disallowedTools`
* `model`
* `maxTurns`
* `isolation: worktree`

### 常见反模式

* 子代理权限与主线程一样宽
* 输出格式不固定，主线程无法消费
* 子任务之间强依赖共享状态

## 十、Prompt Caching 是 Claude Code 内部架构的关键

文章把 Prompt Caching 视为 Claude Code 架构中的核心机制之一。

核心原因有两个：


1. 降低成本
2. 提高高频代理系统的稳定性与吞吐能力

### 文中总结的缓存设计原则

* Prompt 缓存按前缀匹配工作
* 不要在静态系统 Prompt 中放时间戳等动态内容
* 不要在会话中途频繁增删工具
* 不要随意切换模型，否则缓存会重建

作者特别提到：

* 如果需要动态信息，放到后续消息里，不要污染系统 Prompt
* 真要切换模型，更好的方式是通过 Subagent 做模型间交接

### 关于 `defer_loading`

文章还解释了工具延迟加载的价值：

* 工具名常驻
* 完整 schema 按需加载
* 保持缓存前缀稳定
* 避免全量注入工具定义带来的巨大 token 开销

## 十一、验证闭环：没有 Verifier，就没有工程意义上的 Agent

作者认为，"Claude 说完成了"没有意义，必须建立验证体系。

### Verifier 的三个层级

#### 最低层

* 命令退出码
* lint
* typecheck
* unit test

#### 中间层

* 集成测试
* 截图对比
* contract test
* smoke test

#### 更高层

* 生产日志验证
* 监控指标验证
* 人工审查清单

文章的一个重要提醒是：

> 如果一个任务你都说不清楚"怎样才算做对了"，那它大概率也不适合直接丢给 Claude 自动完成。

## 十二、`CLAUDE.md` 应该被视为协作契约，而不是知识库

文章最后给出了一套很实用的 `CLAUDE.md` 设计原则。

### 应该放什么

* 如何 build / test / run
* 关键目录结构与模块边界
* 代码风格和命名约束
* 环境坑
* NEVER 列表
* Compact Instructions

### 不该放什么

* 大段背景介绍
* 完整 API 文档
* 空泛原则
* Claude 自己可以从仓库推断的信息
* 大量背景资料与低频任务说明（这些应放进 Skills）

### 一个很实用的做法

每次纠正 Claude 的错误后，让它更新自己的 `CLAUDE.md`：

> Update your CLAUDE.md so you don't make that mistake again.

作者认为，这会让 Claude 逐步减少重复犯错。但同时也要定期 review，避免历史规则长期过时。

## 十三、作者给出的整体工程化结论

综合整篇文章，可以提炼出以下关键结论：


1. **Claude Code 的问题通常不是 Prompt 问题，而是系统治理问题。**
2. **上下文工程比单纯堆大模型能力更重要。**
3. **Tools、Skills、Hooks、Subagents 应各司其职，不应混用。**
4. **Prompt Caching 会直接影响架构设计与成本结构。**
5. **没有验证闭环的 Agent，不具备真正工程可靠性。**
6. `**CLAUDE.md**` **应短、硬、可执行，只承载持续生效的协作契约。**

## 适合团队立即落地的实践建议

如果从实操角度吸收本文，最值得优先尝试的动作包括：

* 缩短 `CLAUDE.md`，去掉大段背景材料
* 将大文档拆入 Skills supporting files
* 为常见任务建立结构明确的 Skill
* 在高风险路径上加入 Hook
* 用 Subagent 隔离高输出任务
* 为关键任务补齐 Verifier 机制
* 在长任务切换时使用 `HANDOFF.md`
* 用 `/clear`、`/compact`、`/context` 主动治理上下文
